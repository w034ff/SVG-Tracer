## 2. 各検証の詳細

### 検証 1: §4.3 P2（1px の透過余白）によるキーイング動作

#### 検証目的
VTracer 0.6.5 は画像の 5 行（上端、1/4、1/2、3/4、下端）をサンプリングし、完全透過ピクセルが 20%（`0.4 * width`）以上ある場合のみキーイング（透過色除外）を実行する。透過部分が小さいロゴでキーイングが働かない問題が、四辺に 1px の完全透過余白を付与する前処理 P2 によって解決するか確認する。

#### 検証対象
- フィクスチャ: `logo_small_transparency.png`（512×512）
  - 全体の透過ピクセル割合: 約 6.7%（中央に半径 75px の円形透過抜き、17,671px / 262,144px）
  - 5 つのサンプリング行上の透過ピクセル数: y=0, 128, 384, 511 で 0px、y=256 で 150px。合計 150px < 204.8px（`threshold = 512 * 2 * 0.2`）。

#### 実行結果
- **P2 なし**:
  - 生成パス数: 3
  - 透過抜き部分（17,692px）が全て不透明パスとして塗りつぶされた。
  - 元画像（P1 適用）との不一致率: **6.89%**
- **P2 あり（1px 余白付与 → 514×514 でトレース → viewBox で切り落とし）**:
  - 生成パス数: 2
  - 透過抜き部分が正しくキーイングされ、透過のまま保持された（不透明化した透過ピクセル数: 0px）。
  - 元画像（P1 適用）との不一致率: **0.06%**

#### 結論
P2 により、透過率の小さい画像でも確実に VTracer のキーイングが働くことが実証された。自前での `convert` 実装の代替は不要であり、P2 の設計方針で進めることができる。

### 検証 2: §4.3 P3（白黒モードの透過・グレースケール前処理）

#### 検証目的
VTracer の白黒モードは `r < 128` のみで黒を判定しアルファを見ないため、RGB が 0 の透過部分が黒として判定されてしまう。前処理 P3（透過ピクセルを白に合成し、BT.709 で輝度化）によって透過背景の白黒アイコンが正しく変換されるか確認する。

#### 検証対象
- フィクスチャ: `icon_mono_transparent.png`（256×256、透過背景に黒の虫眼鏡アイコン、黒ピクセル数 8,293px、透過ピクセル数 57,243px）

#### 実行結果
- **P3 なし**:
  - 透過ピクセル（R=0）が全て `r < 128` と判定され、全 65,536 ピクセルが黒としてトレースされた（全面真っ黒の正方形が出力）。
  - アイコン形状との不一致率: **87.62%**
- **P3 あり**:
  - 透過ピクセルが白（R=255, G=255, B=255）に合成されるため `r >= 128` となり黒判定から除外された。
  - 実際の黒アイコン部分（8,293px）のみが黒パスとしてトレースされた。
  - 透過背景の基準画像との不一致率: **0.44%**

#### 結論
P3 により、白黒モードで透過背景が黒く塗りつぶされる問題が完全に解消され、期待どおりの形状のみが抽出されることを確認した。

### 検証 3: §4.4 SVG ルート要素の置き換え

#### 検証目的
P2 で余白を付与した画像（幅 W+2, 高さ H+2）の VTracer 出力からルート要素を置換し、`viewBox="1 1 W H"` かつ `width="W" height="H"` に整形することで、元画像サイズで正しく描画・表示されるか確認する。

#### 実行結果
- 置換前の VTracer 出力ルート:
  `<svg version="1.1" xmlns="http://www.w3.org/2000/svg" width="514" height="514">`
- 置換後のルート:
  `<svg xmlns="http://www.w3.org/2000/svg" width="512" height="512" viewBox="1 1 512 512">`
- 検証結果:
  - XML の妥当性: 妥当（resvg / usvg でパース成功）
  - レンダリング寸法: 正確に 512 × 512 ピクセル
  - `<image>` タグの有無: 含まない
  - ピクセル位置整合性: 余白 1px 分が正確にクロップされ、元画像とぴったり位置が一致した。

#### 結論
ルート要素の置換と `viewBox` の指定により、余白を完全に吸収して元画像通りの寸法でベクター出力できることを確認した。

## 3. 発見された設計上の課題と提案

### 白黒モードにおける SVG 背景と品質テスト（design.md §9.2）の整合性

#### 状況
VTracer 0.6.5 の白黒モード（`binary_image_to_svg`）は、`r < 128` のクラスタのみを `<path fill="#000000" ... />` として出力します。**白背景（`r >= 128`）に対するパス（`<rect fill="#ffffff">` 等）は一切出力しません**。
したがって、白黒モードが出力する SVG の背景は常に「透過」となります。

一方で、design.md §9.2 の記述は次のようになっています:
> 変換後の SVG を `resvg` で元画像と同じサイズにラスター化し、§4.3 P1（と白黒時は P3）を適用した元画像と比べる。
> 不一致ピクセル: 透過/不透明が食い違う、または不透明同士で RGB のいずれかの差が `COLOR_TOLERANCE`（32）を超えるピクセル。

これを文字どおりそのまま適用すると次の矛盾が生じます:
1. `icon_mono.png` は元画像が「白背景（不透明）に黒アイコン」です。P3 を適用しても白背景は不透明白のままです。
2. しかし SVG には白背景パスが存在しないため、`resvg` でラスター化するとキャンバスは透過（alpha=0）になります。
3. 比較時に「元画像の白背景（不透明）」と「SVG の背景（透過）」が「透過/不透明の食い違い」と判定され、**白背景部分の全ピクセル（87.7%）が不一致**となってしまいます。
4. 同様に、`icon_mono_transparent.png` は元画像が透過背景ですが、§9.2 の「白黒時は P3 を適用した元画像と比べる」に従うと、P3 によって元画像側が白不透明化されるため、やはり全白ピクセルが不一致判定（87.7%）になります。

#### 解決策の選択肢（設計担当への提案）

1. **案 A（推奨）: 品質テスト時、入力元画像が不透明背景（白背景）の画像については、resvg のキャンバス背景を白（`Color::WHITE`）にしてラスター化する。また透過背景画像については透過背景の元画像と比較する。**
   - 理由: 白黒トレースの主目的は「図形部分を黒ベクターとして抽出すること」であり、背景が透過の SVG になること自体はベクター素材として自然かつ有用であるため。
   - この場合、`icon_mono.png` の不一致率は **0.86%**、`icon_mono_transparent.png` の不一致率は **0.44%** となり、いずれも 1% 未満に収まる。

2. **案 B: 白黒モードの SVG 整形処理（§4.4）で、元画像が不透明だった場合に `<rect width="W" height="H" fill="#ffffff"/>` を背景として SVG に挿入する。**
   - 背景付きの白黒 SVG が求められる場合はこちらになるが、透過ベクターとして使いたい利用者の利便性を損なう可能性がある。

3. **案 C: 品質テストの比較関数において、白黒モード時は「黒ピクセルの位置一致度（IoU や形状差）」のみを比較対象とし、背景の透過/白の差異は不一致としてカウントしない。**

## 4. プリセット値と MAX_MISMATCH_RATIO の推奨値

### プリセット値
design.md §4.5 の初期値表に記載されたパラメータで、いずれのフィクスチャも良好な形状保持とパス数、極めて低い不一致率を達成しました。
したがって、**design.md §4.5 の初期プリセット値を確定値としてそのまま採用することを推奨**します。

### MAX_MISMATCH_RATIO
- 背景整合性を適切に扱った場合の実測最大不一致率は **0.86%**（`icon_mono.png` の角・曲線部）。
- カラー画像（`logo_color.png`）では **0.12%**。
- 曲線単純化によるわずかな境界のズレを許容する安全マージンを考慮すると、当初設計値である **`MAX_MISMATCH_RATIO = 3.0%`** は極めて妥当であり、回帰テストの閾値として適切に機能すると判断できます（より厳格にする場合でも `1.5%` で十分通ります）。
