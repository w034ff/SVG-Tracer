## 2. 各検証の詳細

### 検証 1: §4.3 P2（1px の透過余白）によるキーイング動作

#### 検証目的
VTracer 0.6.5 は画像の 5 行（上端、1/4、1/2、3/4、下端）をサンプリングし、**5 行の透過ピクセルの合計が 0.4 × 幅 以上**（`vtracer` の `should_key_image`: `((width * 2) as f32 * KEYING_THRESHOLD) as usize`、`KEYING_THRESHOLD = 0.2`）ある場合のみキーイング（透過色除外）を実行する。透過部分が小さいロゴでキーイングが働かない問題が、四辺に 1px の完全透過余白を付与する前処理 P2 によって解決するか確認する。

#### 検証対象
- フィクスチャ: `logo_small_transparency.png`（512×512）
  - 全体の透過ピクセル割合: 約 6.7%（中央に半径 75px の円形透過抜き、17,671px / 262,144px）
  - 5 つのサンプリング行上の透過ピクセル数: y=0, 128, 384, 511 で 0px、y=256 で 150px。5 行の透過ピクセルの合計は 150px であり、閾値 204.8px（0.4 × 512）未満。

#### 実行結果
- **P2 なし**:
  - 生成パス数: 3
  - 透過抜き部分（17,692px）が全て不透明パスとして塗りつぶされた。
  - 元画像（P1 適用）との不一致率: **6.89%**
- **P2 あり（1px 余白付与 → 514×514 でトレース → viewBox で切り落とし）**:
  - 生成パス数: 2
  - 透過抜き部分が正しくキーイングされ、透過のまま保持された（不透明化した透過ピクセル数: 0px）。
  - 元画像（P1 適用）との不一致率: **0.06%**

#### 結論
P2 により、透過率の小さい画像でも確実に VTracer のキーイングが働くことが実証された。自前での `convert` 実装の代替は不要であり、P2 の設計方針で進めることができる。

### 検証 2: §4.3 P3（白黒モードの透過・グレースケール前処理）

#### 検証目的
VTracer の白黒モードは `r < 128` のみで黒を判定しアルファを見ないため、RGB が 0 の透過部分が黒として判定されてしまう。前処理 P3（透過ピクセルを白に合成し、BT.709 で輝度化）によって透過背景の白黒アイコンが正しく変換されるか確認する。

#### 検証対象
- フィクスチャ:
  - `icon_mono_transparent.png`（256×256、透過背景に黒の虫眼鏡アイコン、黒ピクセル数 8,293px、透過ピクセル数 57,243px）
  - `icon_mono.png`（256×256、白背景に黒の虫眼鏡アイコン）

#### 実行結果
- **P3 なし（`icon_mono_transparent.png`）**:
  - 透過ピクセル（R=0）が全て `r < 128` と判定され、全 65,536 ピクセルが黒としてトレースされた（全面真っ黒の正方形が出力）。
  - 白背景基準画像との不一致率: **87.62%**
- **P3 あり（決定された比較方法: 白キャンバス描画 × P3 元画像比較）**:
  - `icon_mono_transparent.png`: 生成パス数 1、不一致率 **0.86%**（黒ピクセル 8,293px のみ抽出）。
  - `icon_mono.png`: 生成パス数 1、不一致率 **0.86%**。

#### 結論
P3 により、白黒モードで透過背景が黒く塗りつぶされる問題が完全に解消され、透過背景・白背景のいずれの入力に対しても同一の形状が正確に抽出されることを確認した。

### 検証 3: §4.4 SVG ルート要素の置き換え

#### 検証目的
P2 で余白を付与した画像（幅 W+2, 高さ H+2）の VTracer 出力からルート要素を置換し、`viewBox="1 1 W H"` かつ `width="W" height="H"` に整形することで、元画像サイズで正しく描画・表示されるか確認する。

#### 実行結果
- 置換前の VTracer 出力ルート:
  `<svg version="1.1" xmlns="http://www.w3.org/2000/svg" width="514" height="514">`
- 置換後のルート:
  `<svg xmlns="http://www.w3.org/2000/svg" width="512" height="512" viewBox="1 1 512 512">`
- 検証結果:
  - XML の妥当性: 妥当（resvg / usvg でパース成功）
  - レンダリング寸法: 正確に 512 × 512 ピクセル
  - `<image>` タグの有無: 含まない
  - ピクセル位置整合性: 余白 1px 分が正確にクロップされ、元画像とぴったり位置が一致した。

#### 結論
ルート要素の置換と `viewBox` の指定により、余白を完全に吸収して元画像通りの寸法でベクター出力できることを確認した。

## 3. 決定事項: 白黒モードの品質テストにおける比較方法

### 課題の背景
VTracer 0.6.5 の白黒モード（`binary_image_to_svg`）は、`r < 128` のクラスタのみを `<path fill="#000000" ... />` として出力し、白背景（`r >= 128`）に対するパス（`<rect fill="#ffffff">` 等）は出力しません。そのため白黒モードの SVG は背景が透過になります。
これを透明キャンバスにレンダリングして不透明な白背景の元画像と比較すると、白背景部分全体が「透過/不透明の不一致」と判定されてしまう問題がありました。

### 決定事項
白黒モードの品質テスト（design.md §9.2 / T03）においては、次の手順で比較を行います:
1. **SVG を白いキャンバスにラスター化する**（resvg の `pixmap` をあらかじめ白 `Color::WHITE` で塗りつぶしてから SVG を描画する）。
2. **P3 を適用した元画像（不透明）と比較する**。
3. **入力画像に透過があるかどうかで処理を分けない**（`icon_mono.png` と `icon_mono_transparent.png` の両方に全く同一の手順を適用する）。

この方法により、透過背景の画像と白背景の画像の双方が不一致率 **0.86%** で揃い、透過の有無によらず一貫した検証が可能となりました。

## 4. プリセット値と MAX_MISMATCH_RATIO の推奨値

### プリセット値
design.md §4.5 の初期値表に記載されたパラメータで、対応 5 形式（PNG, JPEG, WebP, BMP, GIF）および白黒の全 14 パターンにおいて、極めて良好な形状保持、安定したパス数、低不一致率（最大 0.86%）を達成しました。
したがって、**design.md §4.5 の初期プリセット値を確定値としてそのまま採用することを推奨**します。

### MAX_MISMATCH_RATIO の見直し
- 全 14 パターンの実測最大不一致率は **0.86%**（白黒アイコンの角・曲線部）でした。
- カラー画像では透過形式で **0.06%〜0.12%**、非透過（JPEG/BMP）でも **0.26%〜0.27%** に収まっています。
- 全ケースが 1.0% 未満を達成していることから、次のいずれかの設定を推奨します:
  - **推奨案（2.0% または 1.5%）**: より厳密なリグレッション検知基準として、当初設計値 3.0% から **`2.0%`**（または `1.5%`）に引き下げる。実測値 0.86% に対しても十分な安全マージンが確保されます。
  - **保守案（3.0%）**: 将来のより複雑なフィクスチャ追加や環境差による微細なラスタライズ差異を許容する安全マージンを広く維持する場合、当初設計値の **`3.0%`** のままでも問題なく機能します。
