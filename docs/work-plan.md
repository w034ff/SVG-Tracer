# 作業計画

[requirements.md](requirements.md)（要件）と [design.md](design.md)（設計）を実装するためのタスク分割と進め方。

## 1. 役割

| 役割 | 担当 | 責務 |
| --- | --- | --- |
| 設計・レビュー | Opus 5.5 | 要件定義・設計・作業計画の作成と更新、タスクごとのレビュー、スパイク結果の設計への反映 |
| 実装・テスト | Gemini 3.8 | タスクの実装とテスト、PR の作成、レビュー指摘への対応 |
| オーナー | 利用者 | 判断が必要な事項の決定、GitHub リポジトリの作成、Windows 実機での確認、マージ |

- `docs/requirements.md` と `docs/design.md` を更新するのは設計担当だけ。実装担当は設計どおりに作れない、または設計が曖昧な場合、実装を止めて PR の説明（またはタスクの報告）に「設計への質問」として書く。
- 実装担当のコーディング規約は [GEMINI.md](../GEMINI.md)。
- リポジトリは https://github.com/w034ff/SVG-Tracer 。オーナーはリポジトリの Settings → Advanced Security で **Secret scanning** と **Push protection** を有効にしておく（API キーなどを含む push を GitHub 側で拒否させるため）。

## 2. 1 タスクの流れ

1. オーナーが Gemini にタスク ID を渡す（例: 「docs/work-plan.md の T03 を実装して」）。
2. Gemini は `main` から `task/T03-<短い名前>` ブランチを作り、実装とテストを行う。
3. §5 の共通の完了条件をすべて満たしたら、PR の説明を日本語で `pr-description.md`（リポジトリの直下、git の管理外）に書き、最後に §2.1 の合図 `agent-status.json` を書く。PR は作らない。PR の説明には次を書く。
   - 先頭に、タスク ID と題の見出し（`# T03 <題>`）と、状態の行（`- 状態: 完了` または `- 状態: 中断`）
   - 対応したタスク ID と、各完了条件をどう満たしたか
   - 設計との差異（あれば）と、その理由
   - 設計への質問（あれば）
4. Opus がブランチの差分（`git diff main...<ブランチ>`）を §6 の観点でレビューする。指摘は作業ツリーの直下の `agent-review.md`（git の管理外）に書く。Gemini は同じブランチで直してコミットし、`pr-description.md` を今の状態に合わせて書き直し、`agent-status.json` を `fixed` にする。
5. 合格したら、Opus が `pr-description.md` の末尾に「手元のレビュー」の節（差し戻しの回数、各回の指摘の要点と直したコミット、レビュー担当が直したもの。差し戻しがなくても「差し戻し: なし」）を足し、push して PR を作り、`agent-review.md` を消す。CI が通ったら、オーナーがマージする。CI の失敗を Gemini に直させるときも、`agent-review.md` で渡す。

差し戻しは PR の前に手元で済ませ、PR は CI とルールセットを通す最後の関門にする。

1 つの PR に 1 つのタスクだけを含める。タスクの範囲外の変更（ついでのリファクタリング、依存の更新など）は含めない。

### 2.1 完了の合図（`agent-status.json`）

PR の説明を書き終えたら、最後の手順として、作業ツリーの直下に `agent-status.json`（git の管理外）を書く。設計担当はこのファイルの変化でレビューを始める。

```json
{ "task": "T03", "state": "done" }
```

- `state` は次のどれか。
  - `done`: 完了。変更はすべてコミット済み。
  - `blocked`: 設計への質問があって止めた（コミットしていない変更が残っていてよい）。PR の説明の状態は「中断」。
  - `fixed`: `agent-review.md` の差し戻しを直した。変更はすべてコミット済み。
- ブランチやコミットは書かない（設計担当が git から読む）。
- `agent-status.json` は Gemini だけが書く。`agent-review.md` は設計担当だけが書き、Gemini は読むだけで、変えたり消したりしない。
- オーナーの環境では、Gemini のターンの終わりに、PR の説明と合図が食い違っていないか、`done`・`fixed` なのに未コミットの変更が残っていないかを確かめる。食い違っていれば、直すように求めるメッセージが届く。

## 4. 各タスクの内容と完了条件

### T00 リポジトリと開発基盤の初期化

内容:
- Tauri 2 + React + TypeScript + Vite のプロジェクトを作り、design.md §3 のディレクトリ構成にする。Cargo ワークスペースに `crates/tracer` と `src-tauri` を含める。
- ESLint を設定し、次のルールをエラーにする: `@typescript-eslint/no-explicit-any`、`@typescript-eslint/consistent-type-assertions`（`assertionStyle: "never"`）、`@typescript-eslint/no-non-null-assertion`、`no-restricted-syntax` による `class` 宣言の禁止。Prettier で整形する。
- `rustfmt`、`clippy`（`-D warnings`）を設定する。
- `.github/workflows/ci.yml` を作り、Windows と Ubuntu で design.md §9.3 の CI 項目のうち、この時点で実行できるもの（fmt、clippy、`cargo test`、lint、型検査、フロントエンドのテスト）を回す。
- `LICENSE`（MIT）を置く。
- `.gitignore` に、ビルド成果物（`target/`、`node_modules/`、`dist/`）に加えて、秘密情報を含み得るファイル（`.env`、`.env.*`、`.gemini/`、`.claude/`、`*.log`、`*.pem`、`*.key`、`*.pfx`）を入れる。

完了条件:
- WSL（WSLg）で `npm run tauri dev` を実行すると空のウィンドウが開く。
- CI が両 OS で成功する。
- `any`、型アサーション、`class` を含むファイルを試しに作ると lint が失敗することを確認し、PR の説明に書く（確認用のファイルはコミットしない）。

完了条件:
- `docs/spike-report.md` に §10 の 1〜4 すべての結果が書かれている。

## 5. 共通の完了条件

すべてのタスクで次を満たす。

- タスクの「完了条件」をすべて満たしている。
- 変更した振る舞いにテストがある。テストは、その機能を壊すと失敗する内容になっている。
- ローカルで次がすべて成功する: `cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`、`npm run format:check`、`npm run lint`、`npm run typecheck`、`npm test`。

- GEMINI.md の規約に従っている。
- 新しい依存を追加した場合、PR の説明にその名前、ライセンス、追加した理由を書いている。

## 6. レビューの観点

Opus は各 PR を次の観点でレビューする。

1. **設計との一致**: design.md の該当箇所どおりか。差異がある場合、その理由は妥当か。
2. **正しさ**: 境界値、エラー経路、並行処理（一括変換、デバウンス）の不具合がないか。
3. **テストの質**: 完了条件のテストが揃っているか。実装をなぞるだけで、壊しても通るテストになっていないか。
4. **セキュリティ**: パスを受け取るコマンドや新しい権限が増えていないか。通信する依存が入っていないか。SVG を `<img>` 以外で表示していないか。API キー・トークン・環境変数の値・個人のファイルパスなど、公開してはならない情報がコードやログ、テスト結果、PR の説明に含まれていないか。
5. **規約**: GEMINI.md（型、コメント、定数、多言語、コミットメッセージ）。
6. **範囲**: タスクの範囲外の変更が含まれていないか。
